# 補貨檢查

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「數字一定要從盤點資料抄，不能自己編」，而且每個數字都要能驗算。

## 什麼時候用

- 跑完 `npm run simulate`，要決定下一版策略每樣菜備幾份時
- 在瀏覽器玩完一天，想看「倉庫盤點」頁的結果該怎麼調整時

## 資料從哪裡來

在 `web-lab` 資料夾執行：

```text
npm run simulate -- plans/策略檔.json --json
```

每一天的 `inventory` 欄位，是那天每樣上架的菜的盤點：

| 欄位 | 意思 | 怎麼驗算 |
|---|---|---|
| `name` | 菜名 | — |
| `stocked` | 早上備了幾份 | 策略檔裡的 `qty` |
| `sold` | 賣出幾份 | 打烊報表 |
| `waste` | 報廢幾份 | 備貨 − 賣出 |
| `missed` | 賣完之後，還有幾位客人想買卻沒買到 | 客人卡片上「賣完了」的數量 |
| `status` | `ok` 正常、`out` 缺貨、`over` 報廢過多 | 規則書「倉庫盤點」 |
| `suggest` | 明天建議備幾份 | 賣出 ＋ 沒買到 |

## 步驟

1. 執行上面的指令，讀每一天的 `inventory`
2. 先驗算：`waste` 有沒有等於 `stocked − sold`？對不上就停下來回報，**不要用錯的資料做建議**
3. 挑出 `status` 不是 `ok` 的菜
4. ★ 建議備貨量要不要再調整（例如：明天客人比較多的日子，要不要多備幾份？多備幾份？）：
   - 只針對 `status` 是 `out`（缺貨）或 `over`（報廢過多）的菜提出調整建議；`ok` 的菜照原本備貨，不另外建議。
   - **基礎建議**：依規則書計算，＝ 賣出（`sold`）＋ 賣完後沒買到（`missed`），也就是盤點資料裡的 `suggest`，只用今天的資料。
   - **隔日調整**：考慮隔天條件後才有的增減，要和基礎建議分開寫，並寫出依據（例如隔天預告的事件、來客數倍率、星等變化、宣傳費），數字要能從資料驗算。
   - 沒有隔日需求的證據時，隔日調整就是 0，直接採用基礎建議。
5. ★ 同一樣菜連續幾天都缺貨或報廢過多，要怎麼提醒：
   - 同一樣菜連續 2 天以上是同一個狀態（都缺貨或都報廢過多），在回報裡標「連續第 N 天缺貨／報廢過多」，並列出每一天的備、賣、報廢、沒買到。
   - 只提醒使用者檢查這樣菜的定價或上架安排，不自己改變建議量的算法。
6. 用下面的回報格式回報

## 回報格式

```text
策略檔：
驗算結果：通過 / 第 N 天的 ○○ 對不上（寫出哪個數字）
第 N 天：
  缺貨：菜名 備 … 賣 … 沒買到 … → 建議 …
  報廢過多：菜名 備 … 賣 … 報廢 … → 建議 …
★ 我想多看一個欄位：隔日調整依據（有就寫出處和數字；沒有就寫「無證據，不調整」）
下一版每天建議的備貨量：
```

## 寫完檢查

- [ ] 每一個數字都能在盤點資料裡找到
- [ ] ★ 我再加一條檢查：資料缺漏或互相矛盾時（例如少了某個欄位、`waste` ≠ `stocked − sold`、`status` 和數字對不起來），要指出是哪一天、哪樣菜、哪個欄位有問題，並停止提出**該筆資料**的備貨建議；其他沒問題的菜照常分析。

## 不准做的事

- 不准修改任何檔案（這個 Skill 只讀不寫，要改策略交給 result-review）
- 不准自己編數字，或用「大概」、「差不多」帶過
- ★ 我再加一條：沒有隔日需求的證據時，不准自行增加固定百分比（例如「一律多備 10%」）；所有調整都要寫出依據。
